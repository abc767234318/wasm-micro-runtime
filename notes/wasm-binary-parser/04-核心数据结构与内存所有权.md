# 04. 核心数据结构、对象关系与内存所有权

## 1. 先分清三层对象

```text
文件层                 模块层                         实例层
.wasm bytes      ->    WASMModule              ->    WASMModuleInstance
Section payload        types/imports/functions       memories/tables/globals
opcode stream          init descriptions             实际可变运行时状态
```

- `WASMSection`：临时文件切片，加载完成即销毁节点。
- `WASMModule`：解析/验证后的不可变模块描述，可用来创建多个实例。
- `WASMModuleInstance`：某次实例化的可变状态；linear memory bytes、table elements、global values 在这里。

把 `WASMMemory` 当成实际 4 GiB memory，或把 `WASMGlobal.init_expr` 当成运行中的 global value，都会读错层次。

## 2. `WASMModule` 是所有模块元数据的 owner/root

核心字段可以分组理解：

```text
WASMModule
|
|-- header: module_type, package_version
|
|-- counts
|   type/import/function/table/memory/tag/global/export/table_seg/data_seg
|   import_function/table/memory/tag/global_count
|
|-- index tables
|   types**
|   imports* + import_functions/tables/memories/tags/globals slices
|   functions**
|   tables*, memories*, tags**, globals*, exports*
|   table_segments*, data_segments**
|
|-- scalar declarations/derived data
|   start_function
|   global_data_size
|   aux data/heap/stack info
|   malloc/free/retain function index
|   possible_memory_grow
|
|-- borrowed file views
|   function.code
|   optional custom sections
|   optional name section buffer
|   optional string literal bytes
|
|-- owned support objects
|   const_str_list
|   ref_type_set/rtt_types
|   br_table cache / fast opcode list / branch hints
|   code_compiled/const pool under each function
|
`-- backend state
    fast-JIT/LLVM-JIT pointers, locks, contexts and threads
```

字段多并不代表一个 `WASMModule` 对象本身包含所有大数据。它主要是 counts、pointers 和少量派生 scalar；大数组按 feature/Section 是否存在分配。

## 3. counts 的两种含义

### Section-local count

`function_count/table_count/...` 通常只统计模块本地定义，不含 imports。

### 绝对索引空间大小

使用时要相加：

```text
function index space size = import_function_count + function_count
table index space size    = import_table_count    + table_count
memory index space size   = import_memory_count   + memory_count
global index space size   = import_global_count   + global_count
tag index space size      = import_tag_count      + tag_count
```

Type、Export、Element/Data segment 则没有对应 import prefix，直接使用各自 count。

### 为什么 imports 又有 `import_count` 又有五种 count

`import_count` 是 Import Section entry 总数，用于分配统一 `WASMImport[]`；五种 count 是五个独立 Wasm index space 的长度。原文件 import 顺序可能交错，但运行时主要按 kind 的索引访问。

## 4. `WASMType` 家族

### 无 GC 构建

```c
typedef struct WASMFuncType WASMType;
typedef WASMType *WASMTypePtr;
```

类型表只能放 function type。`WASMFuncType` 的 `types[]` 连续存 params/results：

```text
index                    0 ... param_count-1 | param_count ... total-1
meaning                         params       | results
```

为什么不用两个 pointer：一个尾数组少一次分配、少一个 pointer；结果开始位置由 `types + param_count` 直接算出。

### GC 构建

`WASMType` 变为公共 header：

```text
WASMType
  ^
  | first member
  +-- WASMFuncType
  +-- WASMStructType
  `-- WASMArrayType
```

C 没有基类，WAMR 依赖“公共 header 必须是派生 struct 的第一个成员”。`WASMType *` 可以安全指向任一对象开头，再检查 `type_flag` 后 cast。

这种手工多态的纪律：

1. 公共成员必须在 offset 0。
2. cast 前必须判别 tag。
3. 析构也按 tag dispatch。
4. 任一配置改变 header 布局时，所有派生 struct 同时重新编译。

### `ref_count` 不是 GC object reference count

这里的 `WASMType.ref_count`/无 GC 的 func type ref_count 用于“多个 type table slot 共享等价 type 描述”的模块加载期去重。它不是 Wasm GC heap object 的运行期引用计数。

## 5. Reference type 的压缩表示

多数 valtype 一个 byte 足够。GC 的 `(ref null typeidx)` 需要：

```text
nullable + heap type(kind or typeidx)
```

WAMR 采用两层：

```text
主数组 local_types[i]/types[i]/field_type
  -> 总保存第一个 byte

只有 multi-byte 项：
WASMRefTypeMap { index=i, ref_type=WASMRefType* }
```

`WASMRefType` 本身是 union：

- `RefHeapType_TypeIdx` 保存自定义 typeidx。
- `RefHeapType_Common` 保存 func/extern/any/eq/i31/struct/array 等抽象 heap type。

`module->ref_type_set` 会 intern 完整 ref types，多处 map 可指向同一个不可变对象。好处是稀疏、去重；代价是任何类型访问 helper 都要判断“单字节还是需要 map”。

## 6. `WASMImport` 的统一块与切片

内存示意：

```text
module->imports (唯一 owner，需要 free 的基地址)
|
v
+----------+----------+----------+----------+----------+
| functions| tables   | memories | tags     | globals  |
+----------+----------+----------+----------+----------+
^          ^          ^          ^          ^
|          |          |          |          |
import_    import_    import_    import_    import_
functions tables     memories   tags       globals
```

五个 slice pointer 不能分别 free。`wasm_loader_unload()` 只 free `module->imports`。

每个 `WASMImport` 的 union 足够容纳最大的 descriptor。连续数组中小 descriptor 也占 union 最大大小，这是用单块分配换取简单索引和释放；如果各 kind 数量很大且 union 成员差异极大，分开数组更省空间，但会增加分配和通用处理复杂度。

### 链接字段为什么放在 parse object 中

`WASMFunctionImport` 同时保存声明的 `func_type` 和解析后的 native function pointer/signature。Import parsing 与链接在 WAMR 中相邻进行，所以同一对象承担“声明 + resolution cache”。`no_resolve` 则只填声明部分。

Multi-module 构建还保存 linked module/object 指针，避免每次调用按名字查找。

## 7. `WASMFunction` 的四组信息

### 签名和 locals

```text
func_type -> params/results
local_count/local_types -> 只含显式 locals，不含 params
local_offsets -> params + locals 的 cell offset
```

若签名 `(i32, i64) -> i32`，locals 是 `[f32, i64]`：

```text
logical local index : 0(param i32) 1(param i64) 2(local f32) 3(local i64)
cell width          : 1            2            1            2
local_offsets       : 0            1            3            4
frame end offset    : 6
```

所以 `local_offsets` 用 `uint16`，fast interpreter 又把 operand offset 压为 `int16`；loader 会拒绝超过可表示范围的 frame。

### 原始 code view

```c
uint32 code_size;
uint8 *code;
```

指向 locals declarations 后、function expression 第一个 opcode。它通常借用原 binary，并可能被 classic interpreter 预处理原地改写。

### 验证结果

```text
max_stack_cell_num
max_block_num
has_op_memory_grow / has_op_func_call / has_memory_operations / ...
```

这些字段让 instance frame 分配和 JIT 决策不必再扫 opcode。

### Fast interpreter 产物

```text
code_compiled/code_compiled_size
consts/const_cell_num
```

`code_compiled` 是 owner pointer，由 module unload 释放。`consts` 把 dedup 后的 i64/f64、i32/f32、v128 raw values 聚合为 cell pool，compiled code 引用固定 offset。

fast interpreter 预处理完后，执行主要依赖 `code_compiled`，这是输入 binary 有机会提前释放的根本原因。但 `WASMFunction.code` 字段本身仍是借用指针，其他功能也可能保留 binary 内部指针；应由 `wasm_runtime_is_underlying_binary_freeable()` 统一判定，而不是遍历 struct 自行推测。

## 8. `WASMMemory` 与 `WASMTable`

### Module declaration

`WASMMemory` 只有 limits 和 page size。`WASMTable` 只有 table type 和可选 initializer expression。它们适合连续数组，因为每项在给定构建配置中大小相同。

### Instance state

对应的 `WASMMemoryInstance` 才有 actual memory pointers、bounds、heap handle；`WASMTableInstance` 才有当前 size 和 element storage。

这种 descriptor/instance 分离支持：

- 一个 module 创建多个互不影响的 instances。
- module 元数据只读共享。
- 解析不立即申请巨大 linear memory。

### limits 为什么会被规范化

内部 `max_page_count/max_size` 是 runtime 实际允许值，可能受 platform/pool/WAMR cap 限制；`num_bytes_per_page` 也可能在确认不可 grow 时调整。因此 `WASMMemory` 不是精确 round-trip binary AST。

需要重建原文件时必须保留原 binary，而不是从 `WASMModule` 序列化。

## 9. `WASMGlobal` 与 `WASMValue`

`WASMValue` 是所有 scalar/raw value 的 union：i32/u32/i64/u64/f32/f64/v128/ref，以及 GC initializer 的辅助 payload。

union 的优点：一个 initializer object 不管值类型都固定大小。正确解释依赖外部的 `init_expr_type`/valtype；union 自己不携带 tag。

`InitializerExpression`：

```text
init_expr_type
u.unary.v                       常量/global.get/ref.func/GC payload
或
u.binary.l_expr/r_expr          extended const add/sub/mul 树
```

为什么二元表达式用指针树而不放通用 opcode vector：当前支持的 extended const op 很少，树能在实例化时直接递归求值；但每个二元节点会产生小分配，深表达式的碎片/清理更复杂。

## 10. Element/Data segment 的不同分配策略

### Element

`WASMTableSeg *table_segments` 是连续 descriptor 数组；每段的 `init_values` 另分配连续表达式数组。

因为 descriptor 定长、value count 变长，采用“两层连续数组”最自然。

### Data

`WASMDataSeg **data_segments` 是 pointer array，每个 descriptor 独立分配，payload 又可借用或单独拥有。

这使失败清理可以逐项判断：

```text
data_segments[i] 是否已经创建？
data_segments[i]->is_data_cloned 是否需要 free data？
```

代价是比 element 多一些小分配和指针间接访问。

## 11. 字符串 intern list

当不能原地借用 binary 中的 name 时，WAMR 分配：

```text
+----------------+------------------+
| StringNode     | chars + '\0'     |
+----------------+------------------+
                  ^ node->str
```

同一个 allocation 同时装链表节点和字符串，减少一次 malloc。插入前线性搜索已有字符串，实现简单的 interning。

复杂度是 O(number_of_names²) 的最坏情况，但 typical Wasm import/export name 数不大；引入 hash table 会增加常驻代码和内存。GC ref types 数量/查询更高时，WAMR 才使用真正的 HashMap，这体现了按工作负载选择数据结构。

## 12. Section view 与 Custom linked list

二者都是链表，但生命周期不同：

- `WASMSection`：临时，payload 借用，`load()` 返回前节点全释放。
- `WASMCustomSection`：module 生命周期，节点 owned、name/content borrowed。

Custom Section 数未知且通常很少，用链表比先扫描统计/分配数组更简单；核心 Section 数量与顺序固定，临时链表又便于跨段预查。

## 13. Loader context 的临时栈

`WASMLoaderContext` 是单个 function 验证/lowering 的 workspace：

| 字段 | 作用 |
| --- | --- |
| `frame_ref` | operand type stack，按 cell 表示 |
| `frame_reftype_map` | GC multi-byte ref 的并行稀疏信息 |
| `frame_csp` | control stack，每项是 `BranchBlock` |
| `frame_offset` | fast interp operand 所在 frame slot |
| `dynamic_offset/max_dynamic_offset` | 临时栈槽分配 |
| `i32/i64/v128_consts` | 第一遍收集的常量 |
| `p_code_compiled` | NULL 表示计数遍，非 NULL 表示 emit 遍 |

这些数组从小容量开始，按固定增量 `MEM_REALLOC`。为什么不按 code_size 一次估算：code bytes 与 operand/control stack 深度没有简单紧上界，按需增长能让普通小函数保持小 workspace。

`BranchBlock` 保存：

- label kind 和 block signature。
- 原 code start/else/end。
- 进入 block 时的 stack height。
- polymorphic/unreachable 状态。
- fast interp 的动态 slot、compiled label 和 patch list。
- GC 对 non-nullable local use 的 mask。

这就是验证算法里的 control stack frame，而不是 runtime 每次执行都创建的 block object。

## 14. 所有权总表

| 对象/字段 | 分配者 | owner | 是否借用 binary | 释放位置 |
| --- | --- | --- | --- | --- |
| `WASMSection` node | `create_sections` | load 临时流程 | body 是 | `destroy_sections` |
| `WASMModule` | `create_module` | runtime caller | 否 | `wasm_loader_unload` |
| `module->types` | type parser | module | 否 | unload + ref-counted type destroy |
| `module->imports` | import parser | module | names 可能借用 | unload 只 free 基地址 |
| `WASMFunction` | function parser | module | `code` 是 | unload |
| `code_compiled/consts` | prepare bytecode | function/module | 否 | unload |
| `tables/memories/globals/exports` | 各 Section parser | module | export names 可能借用 | unload |
| `tags[i]` | tag parser | module | 否 | unload 逐项 + pointer array |
| `table_segments[i].init_values` | element parser | module | 否 | unload 逐段 |
| `data_segments[i]` | data parser | module | data 视 flag | unload 逐段 |
| `const_str_list` | string helper | module | 否 | unload linked list |
| `WASMCustomSection` node | custom parser | module | name/content 是 | common custom-section destroy |
| string literal arrays | stringref parser | module | literal bytes 是 | unload arrays |
| `WASMLoaderContext` | prepare bytecode | 当前函数调用 | code 是 | prepare 尾部 destroy |

## 15. `wasm_loader_unload()` 为什么释放顺序重要

大体顺序是：

1. 停止/等待 JIT threads，防止并发访问即将释放的 module。
2. 销毁 JIT context/pointers。
3. imports/functions/tables/memories/globals/tags/exports/segments。
4. types、字符串、cache/custom metadata。
5. locks/hash maps/RTT。
6. module 本身。

Initializer expression 的 GC payload 需要查询 `module->types` 才知道递归内容，所以 globals/table/data/elem 的 expression 必须在 types 之前销毁。这个依赖就是“析构顺序也是数据结构设计的一部分”。

失败路径也复用同一个 unload：loader_malloc 清零保证尚未创建的 pointer/count 为 0，逐项循环只处理已挂入对象。

## 16. 设计取舍总结

| 设计 | 获得 | 代价 |
| --- | --- | --- |
| 借用 binary pointer | 少 copy、低峰值内存 | 生命周期耦合、可能原地改写 |
| 尾数组/连续块 | 少 malloc、缓存友好 | size 计算和调试更难 |
| tagged union | 压缩互斥状态 | 必须严格按 tag 访问 |
| 两遍扫描 | 精确布局、少 realloc | 增加一次读取、两遍逻辑需同步 |
| type/ref interning | 常驻内存小、比较快 | shared ownership/refcount/hash set |
| compile-time feature | 最小产物、零运行时分支 | 布局/代码组合复杂、测试矩阵大 |
| parse+validate+lower 融合 | 少中间 AST/遍历 | loader 大、职责耦合、难复用为工具 |
