## 2. 最有效的 `rg` 导航命令

找所有 Section parser：

```bash
rg -n '^load_.*section\(' core/iwasm/interpreter/wasm_loader.c
```

找一个结构的创建、读取、释放：

```bash
rg -n 'WASMTableSeg|table_segments' core/iwasm -g '*.[ch]'
```

找 opcode 在 parser、block scanner、interpreter、compiler 的所有路径：

```bash
rg -n 'WASM_OP_MEMORY_INIT' core -g '*.[ch]'
```

找 feature 对 loader 布局/行为的影响：

```bash
rg -n 'WASM_ENABLE_MEMORY64' \
  core/iwasm/interpreter/wasm_loader.c \
  core/iwasm/interpreter/wasm.h
```

找错误消息由哪条校验产生：

```bash
rg -n 'function and code section have inconsistent' core
```

找所有权的最好办法：

```bash
rg -n 'data_segments|is_data_cloned' \
  core/iwasm/interpreter/wasm_loader.c
```

一定同时看 allocation 和 `wasm_loader_unload()`。

## 3. 阅读一个 Section parser 的固定步骤

以任意 `load_X_section()` 为例：

1. 在 `wasm.h` 找 Section ID 和目标结构定义。
2. 在 `load_from_sections()` 看调用参数，尤其 ownership flags。
3. 从函数顶部列出 `p/p_end/count/total_size`。
4. 写出磁盘 grammar，不急着看校验分支。
5. 标记 first scan/second scan。
6. 标记每次 allocation 的 owner。
7. 标记索引空间是 absolute 还是 local-only。
8. 列出 feature `#if` 导致的 grammar 差异。
9. 看结束处的 `p == p_end`。
10. 去 unload 找对称释放。
11. 去 runtime instantiate 找这些字段怎样被消费。
12. 用 WABT 生成一个只含该段的最小 case 对照 raw bytes。

如果只看 parser 而不看 consumer，很难理解“为什么内部字段这样设计”。

## 4. 阅读一个 opcode 的固定步骤

假设研究 `memory.init`：

1. `wasm_opcode.h`：确认 prefix/subopcode 数值。
2. `wasm_loader_prepare_bytecode()`：immediate、索引、stack effect、feature gate、emit。
3. `wasm_loader_find_block_addr()`：执行时扫描怎样跳过它。
4. `wasm_interp_classic.c`：classic representation 怎样消费。
5. `wasm_interp_fast.c`：compiled representation 怎样消费。
6. `aot`/`fast-jit`：若涉及 compiler，检查 lowering。
7. DataCount/Data Section：确认跨段 index space 来源。
8. tests：搜索 valid、malformed、feature-disabled case。

只在 enum 中看到 opcode 不代表 loader/某执行后端支持它；只有所有必需路径一致才算支持。

## 5. 新增/修改 Section 时的检查清单

### Container 层

- [ ] 在 `wasm.h` 定义 ID，并受正确 feature macro 包围。
- [ ] 加入 `section_ids[]` 的规范顺序。
- [ ] 决定允许一次还是多次；只有 Custom 默认可重复/任意插入。
- [ ] mini loader 是否也要识别。

### Module 表示

- [ ] `WASMModule` 加 count/pointer/scalar。
- [ ] 明确 pointer owned 还是 borrowed。
- [ ] size 乘加用 u64 计算并有上限。
- [ ] 若对象变长，决定尾数组、pointer array 或两层连续数组。
- [ ] 若受 feature 宏影响，所有 producer/consumer 用同一宏。

### Parser

- [ ] 所有 byte/LEB read 有 end check。
- [ ] vector count 累加/乘法检查溢出。
- [ ] index 在对应 import+local 空间校验。
- [ ] name 验证 UTF-8。
- [ ] Section 尾要求 `p == p_end`。
- [ ] 失败前未挂入 module 的临时对象被释放。

### Consumer/lifecycle

- [ ] instantiate/runtime/compiler 使用新字段。
- [ ] `wasm_loader_unload()` 对称释放，且顺序不依赖已释放对象。
- [ ] memory consumption profiler 统计新 allocation。
- [ ] binary-freeable 路径处理所有长期借用内容，并验证 `wasm_runtime_is_underlying_binary_freeable()` 的结果。
- [ ] custom/load-from-sections 路径行为明确。

### 验证

- [ ] 空段、1 项、多项。
- [ ] truncated LEB/payload。
- [ ] count 过大和乘法溢出。
- [ ] duplicate/out-of-order。
- [ ] invalid index/type/feature disabled。
- [ ] full loader 与 mini loader 的预期差异。

## 6. 新增/修改 opcode 时的检查清单

- [ ] core/prefix opcode number 和 mnemonic。
- [ ] checked immediate decoder。
- [ ] operand stack pop/push 和 polymorphic state。
- [ ] control stack/branch target signature。
- [ ] index/mutability/subtyping/alignment/lane 检查。
- [ ] `wasm_loader_find_block_addr()` 能正确跳过 immediate。
- [ ] classic preprocessing 不与 internal opcode 冲突。
- [ ] fast preprocessing first pass size 与 second pass emit 完全一致。
- [ ] constant pool/operand offset/branch patch 如需要。
- [ ] classic interpreter handler。
- [ ] fast interpreter handler/table。
- [ ] AOT/JIT/fast-JIT consumer。
- [ ] feature-disabled 时给出明确 unsupported/feature error。
- [ ] valid execution、malformed immediate、stack underflow、bad index 测试。

反汇编器最基本的完整性标准是“任一合法 opcode 都能精确停在下一条边界”；validator 还要完成后续所有语义项。

## 7. Full loader 与 mini loader 的审计方法

不要假设同名函数内容一致。建议按 function list 对照：

```bash
rg -n '^load_.*section\(' \
  core/iwasm/interpreter/wasm_loader.c \
  core/iwasm/interpreter/wasm_mini_loader.c
```

再按 feature 比较：

```bash
rg -o 'WASM_ENABLE_[A-Z0-9_]+' \
  core/iwasm/interpreter/wasm_loader.c | sort -u

rg -o 'WASM_ENABLE_[A-Z0-9_]+' \
  core/iwasm/interpreter/wasm_mini_loader.c | sort -u
```

当前 full loader 有 GC、stringref、branch hints、debug bytecode tracking 等 mini loader 不具备的路径。最重要的边界来自官方构建说明：mini loader 跳过完整性检查，只能加载来源可信、已预先验证的 Wasm。

设计上它们共享：

- 相同 loader API。
- 相同 `WASMModule` 核心结构。
- 相同 runtime/解释器 consumer。

但“接口相同”不意味着安全属性和 proposal coverage 相同。

## 8. Feature 宏分层

可以按影响范围分组：

### 改 binary grammar/索引空间

```text
WASM_ENABLE_GC
WASM_ENABLE_REF_TYPES
WASM_ENABLE_BULK_MEMORY
WASM_ENABLE_MEMORY64
WASM_ENABLE_MULTI_MEMORY
WASM_ENABLE_TAGS
WASM_ENABLE_STRINGREF
WASM_ENABLE_EXCE_HANDLING
WASM_ENABLE_TAIL_CALL
WASM_ENABLE_SIMD
WASM_ENABLE_SHARED_MEMORY
```

### 改内部 code representation

```text
WASM_ENABLE_FAST_INTERP
WASM_ENABLE_LABELS_AS_VALUES
WASM_CPU_SUPPORTS_UNALIGNED_ADDR_ACCESS
WASM_ENABLE_SIMDE
WASM_ENABLE_DEBUG_INTERP
```

### 改链接/后端/派生字段

```text
WASM_ENABLE_MULTI_MODULE
WASM_ENABLE_WAMR_COMPILER
WASM_ENABLE_FAST_JIT
WASM_ENABLE_JIT
WASM_ENABLE_LAZY_JIT
```

### 改 metadata 保留

```text
WASM_ENABLE_CUSTOM_NAME_SECTION
WASM_ENABLE_LOAD_CUSTOM_SECTION
WASM_ENABLE_BRANCH_HINTS
WASM_ENABLE_DUMP_CALL_STACK
```

阅读一个 `#if` 时先判断它属于哪层，才能知道关闭后是“拒绝输入”“换内部表示”还是“只少一个辅助功能”。

## 9. Parser 不等于 validator，不等于 linker

在 WAMR 中三者写在同一大函数链里，但概念上应拆开：

| 层 | 问题 | 例子 |
| --- | --- | --- |
| syntactic parse | bytes 能否按 grammar 消费 | LEB 是否结束、Section size 是否匹配 |
| module validation | 声明/指令是否合法 | typeidx 越界、stack mismatch、duplicate export |
| import resolution/link | 外部依赖是否存在且兼容 | native function lookup、multi-module export |
| execution lowering | 怎样让后端快速执行 | local cell offsets、code_compiled、branch patch |

`no_resolve` 只能跳过部分 link，不跳过 binary/类型验证。mini loader 则改变 syntactic/integrity 的安全保证。调试错误时先归类，能快速缩小源码范围。

## 11. 最后形成的心智模型

面对任意 `.wasm` byte，按下面六问定位：

```text
1. 它属于哪个 Section envelope？
2. 这个字段是什么编码，p 读完应到哪里？
3. 它进入哪个 Wasm index space？imports 是否在前？
4. WAMR 转成哪个结构，字段是 owned 还是 borrowed？
5. 哪些 feature 改变 grammar、布局或 consumer？
6. unload/instance/interpreter 最终怎样使用它？
```

能连续回答这六问，就不再是在“跟着一个 17000 行 switch 猜”，而是在按体系阅读 WAMR parser。
