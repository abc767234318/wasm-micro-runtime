# 01. WAMR Loader 的大型 C 项目设计导读

对没有大型 C 项目经验的读者，`wasm_loader.c` 最难的地方通常不是 WebAssembly，而是它把对象模型、错误处理、内存管理和 feature 裁剪都用 C 的低层手段表达出来。本篇先建立这些阅读习惯。

## 1. 指针游标就是 C 版 BinaryReader

Section parser 几乎都采用同一模板：

```c
const uint8 *p = buf, *p_end = buf_end;

read_leb_uint32(p, p_end, count);
for (i = 0; i < count; i++) {
    CHECK_BUF(p, p_end, 1);
    kind = read_uint8(p);
    /* 继续消费字段 */
}

if (p != p_end) {
    /* section size mismatch */
}
```

可以把它脑补成一个对象：

```text
BinaryReader {
    cursor = p
    limit  = p_end
}
```

但 C 中没有方法调用，宏直接修改局部变量 `p`。例如 `read_leb_uint32(p, p_end, x)` 成功后会把 `p` 移到该 LEB128 后面，失败则跳到当前函数的 `fail:`。

这种设计的原因：

- 不创建 reader 对象，没有虚函数或额外状态。
- 热路径只做指针加法，适合 MCU。
- 子解析函数接收 `const uint8 **p_buf`，成功时把新游标写回；这相当于 C 里的“可变引用”。
- 每个 Section 都有独立的 `p_end`，天然形成安全边界。

阅读时始终标出三个位置：字段开始前的 `p`、字段结束后的 `p`、允许访问的最后位置 `p_end`。

## 2. `uint8 **`/`const uint8 **` 为什么出现

下面的函数签名表示“既返回解析结果，也推进调用方的游标”：

```c
static bool load_memory(const uint8 **p_buf,
                        const uint8 *buf_end,
                        WASMMemory *memory, ...);
```

调用关系是：

```c
const uint8 *p = ...;
load_memory(&p, p_end, memory, ...);
```

- `p` 是一个 `const uint8 *`。
- `&p` 才是 `const uint8 **`。
- 子函数先用局部 `p = *p_buf`；全部成功后才执行 `*p_buf = p`。

“成功才提交游标”是一种轻量事务语义。失败时调用方的游标不一定有意义，但不会在字段解析一半时被悄悄提交。

## 3. `count + pointer` 是 C 中的 vector

WAMR 大量使用：

```c
uint32 function_count;
WASMFunction **functions;
```

这等价于只读意义上的 `vector<WASMFunction *>`：

- `function_count` 决定合法下标和分配大小。
- `functions` 指向连续元素。
- 没有 capacity，因为模块加载后大部分表不再增长。

为什么不用链表：

- Wasm 二进制已经在 vector 前给出 count，可以一次精确分配。
- 索引是 Wasm 语义的一部分，数组可 O(1) 查找。
- 连续内存缓存友好，分配次数少。

为什么某些表是 `T *`，某些是 `T **`：

- `WASMMemory *memories`、`WASMGlobal *globals`：对象定长，直接连续摆放。
- `WASMFunction **functions`、`WASMType **types`：每个对象大小不同，或需要共享/替换对象，所以数组保存指针。
- `WASMDataSeg **data_segments`：payload 的借用/复制策略和逐项清理更方便用独立对象表达。

这不是随意风格差异，而是对象是否变长、是否共享以及释放粒度的结果。

## 4. 尾数组：一次分配结构体和变长数据

`WASMFuncType` 末尾有 `uint8 types[1]`；实际分配不是固定 `sizeof(WASMFuncType)`：

```c
total_size = offsetof(WASMFuncType, types)
             + param_count + result_count;
type = loader_malloc(total_size, ...);
```

内存形状：

```text
+-----------------------+
| WASMFuncType 固定字段 |
+-----------------------+ <- offsetof(types)
| param types           |
| result types          |
+-----------------------+
```

这是旧式 flexible-array idiom；现代 C 常写 `types[]`。优点是只分配一次、局部性好、释放一次。代价是：

- 必须用 `offsetof` 和溢出安全的乘加计算。
- 不能对对象做普通的浅拷贝来复制尾部。
- 调试器只知道声明中的一个元素，实际长度要看 count。

同样的模式还用于：

- `WASMFunction` 后紧跟展开后的 `local_types`。
- `WASMStructType` 后跟 fields，再跟 GC reference offset table。
- `WASMStructNewInitValues.fields[1]`、`WASMArrayNewInitValues.elem_data[1]`。
- `BrTableCache.br_depths[1]`。

## 5. union：让一种 Section entry 承载多种 kind

Import entry 的 binary grammar 是：

```text
module_name, field_name, kind, descriptor(kind)
```

WAMR 对应：

```c
typedef struct WASMImport {
    uint8 kind;
    union {
        WASMFunctionImport function;
        WASMTableImport table;
        WASMMemoryImport memory;
        WASMGlobalImport global;
        WASMTagImport tag;
        struct { char *module_name; char *field_name; } names;
    } u;
} WASMImport;
```

为什么用 union：同一个 import 只可能属于一种 kind。如果把所有 descriptor 都并排放在 struct 中，每个函数导入也会为 table/memory/global 字段付费。

`u.names` 是一个值得学习的 C 技巧：所有具体 import struct 的前两个字段也都是 `module_name/field_name`，所以可以通过 union 的公共前缀统一读取名字。但这种技巧依赖布局约定，新增成员或调整字段时必须谨慎；它不是 C++ 的继承。

读取 union 的纪律：先看 `kind`，再访问对应成员。访问错误成员在语义上就是 bug。

## 6. 两遍扫描：用 CPU 换峰值内存和简单布局

`load_import_section()` 先扫描一遍，只统计各 kind 数量；然后：

```text
module->imports 一整块
  [functions][tables][memories][tags][globals]
       ^         ^        ^       ^      ^
  五个 slice 指针分别指向各自开头
```

第二遍才真正解析并填充各 slice。

Type/locals 的 GC 分支也会先数“有多少 multi-byte reference type”，再精确分配 map，第二遍填值。

为什么不边读边 realloc：

- 二进制 buffer 已在内存中，重复顺序读取很便宜。
- 精确分配，降低碎片和峰值内存。
- 同 kind 的 imports 连续，运行时按函数/表/内存索引访问简单。
- 避免保存临时 AST。

代价是加载 CPU 增加，源码中必须保证两遍对变长字段的跳过规则完全一致。

## 7. 索引空间不是数组下标的同义词

Wasm 的 function/table/memory/global/tag 索引空间都遵守：

```text
[imported items][module-defined items]
```

例如绝对函数索引 `funcidx` 的解析：

```c
if (funcidx < module->import_function_count)
    import = &module->import_functions[funcidx];
else
    func = module->functions[funcidx - module->import_function_count];
```

所以：

- `module->functions[0]` 不是必然的 Wasm `func[0]`。
- 若有 3 个 imported functions，`module->functions[0]` 的绝对 `funcidx` 是 3。
- name custom section、export、start、call、ref.func 使用的都是绝对索引空间。

这是写 dump/disassembler 时最常见的 off-by-import-count 错误。

## 8. 借用、拥有与原地改写

C 没有生命周期类型，WAMR 靠参数、flag 和 unload 代码维护所有权。

主要情况：

| 指针 | 默认关系 | 何时必须复制 |
| --- | --- | --- |
| `WASMSection.section_body` | 借用原 binary | Section 节点在加载后就释放，不长期保存 |
| `WASMFunction.code` | 借用 Code Section 中的 expression | 模块生命周期内 binary 必须仍有效，或上层按约定管理 |
| `WASMDataSeg.data` | 借用或拥有 | binary 标记可释放时，loader clone payload，并设 `is_data_cloned` |
| import/export/name 字符串 | 借用并原地 NUL 化，或 intern 后拥有 | 由 `reuse_const_strings` 决定 |
| custom section content | 借用原 binary | 开启 `WASM_ENABLE_LOAD_CUSTOM_SECTION` 时尤其要保证 buffer 生命周期 |

`wasm_const_str_list_insert()` 的优化非常“C”：当原文件 buffer 可长期保留时，它把字符串向前移动一个字节，覆盖原来的 LEB 长度尾字节，并在末尾写 `\0`，从而不为 C string 单独分配内存。也就是说 loader 的输入类型虽然是 `uint8 *`，并不保证加载后字节仍与原文件完全相同。

这解释了两个实践规则：

1. 要做文件级 dump/offset 对照，优先在 `wasm_runtime_load()` 前保存或读取原文件。
2. 要释放输入 buffer，先用 `LoadArgs.wasm_binary_freeable=true` 声明这个意图，加载成功后再以 `wasm_runtime_is_underlying_binary_freeable(module)` 的返回值为准；不要只看输入 flag 就释放。

`wasm_binary_freeable` 是“请 loader 复制部分长期字段”的意图，不是对所有构建配置的寿命保证。当前 bytecode runtime 仅在 fast interpreter 可以脱离原 binary 且不受 lazy JIT 等条件阻止时才会查询为 true；GC string literal 仍直接指向 binary 时也会返回 false。这是 C 项目常见的“调用者声明意图 + 库报告实际能力”两阶段协议。

## 9. `loader_malloc()` 为什么总是清零

`loader_malloc()` 做三件事：

1. 拒绝 `size >= UINT32_MAX`，适配 WAMR allocator 的 32 位 size。
2. 调用 `wasm_runtime_malloc()`，从而服从 runtime 配置的 pool/system/custom allocator。
3. `memset(..., 0, size)`。

清零让大量构造代码可以只填写非零字段，也让失败清理能安全判断 `if (ptr)`。代价是分配有额外写内存成本，而且“字段未初始化”和“字段合法为 0”在调试时难区分。

分配表达式一律先用 `uint64 total_size` 计算，再交给 `loader_malloc()`，目的是防止 `count * sizeof(T)` 在 32 位中先溢出。

## 10. `goto fail` 是 C 的单出口清理机制

宏中常见：

```c
if (!read_leb(...))
    goto fail;
```

`goto` 在这里不是任意跳转，而是模拟异常展开：

```text
深层检查失败
    -> 跳到本函数 fail
    -> 释放本函数临时资源或返回 false
    -> 上层返回 false
    -> wasm_loader_unload(module) 统一释放已经挂到 module 的对象
```

理解规则：

- 已经挂入 `module` 的长期对象，通常交给 `wasm_loader_unload()`。
- 还没挂入 module 的临时对象，当前函数必须在 `fail:` 释放。
- 宏依赖局部变量名 `error_buf/error_buf_size` 和 `fail:` label；复制宏到别的函数时必须满足隐含契约。

## 11. 编译宏不是装饰，而是在改变类型布局

例如 `WASM_ENABLE_GC` 不只多几段 `switch case`，还会：

- 把 `WASMType` 从 `WASMFuncType` 别名变成 func/struct/array 的公共基类。
- 给 function/global/table/local 增加 reference-type map。
- 改变 `WASMModule` 字段和 unload 路径。
- 改变 opcode/constant expression 验证。

因此不能只读当前 IDE 灰掉后的代码。分析一个字段时至少问：

- 它被哪个 `WASM_ENABLE_*` 包围？
- 这个宏为 0 时，同名 typedef 是否变成另一个类型？
- `wasm_loader_unload()` 是否有对称的释放分支？
- mini loader 是否支持同一个 feature？

完整 loader 当前涉及四十余个 feature 宏。第 7 篇给出按 feature 检查的方法。

## 12. 内部结构为什么不照抄磁盘格式

磁盘格式为体积和流式传输优化：LEB128、tagged union、索引引用、locals 分组压缩。运行时结构为高频访问优化：本机整数、直接指针、展开后的 locals、预计算 cell offset、按 kind 分组的 imports。

典型转换：

| 磁盘表示 | 内部表示 | 原因 |
| --- | --- | --- |
| LEB128 count/index | `uint32` | 执行时不反复解码 |
| function 的 `typeidx` | `WASMFuncType *func_type`，GC 下另保留 `type_idx` | 常用路径直接解引用，同时保留名义类型信息 |
| locals `(n, valtype)` 分组 | 每个 local 一个 `local_types[i]` | `local.get/set` O(1) 得类型 |
| local 的逻辑序号 | `local_offsets[]` 中的 cell offset | interpreter frame 按 32-bit cell 访问 |
| elem 中的 `funcidx` | `InitializerExpression(ref.func)` 数组 | 与表达式形式的 elem segment 统一 |
| UTF-8 name bytes | NUL 结尾 `char *` | 直接使用 C 字符串 API |

核心取舍是：加载期多做一次工作，换执行期更少分支、更少解码和更紧凑的常驻对象。
