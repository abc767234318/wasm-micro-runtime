# 一步步理解 WAMR 的内存池（Memory Pool）

## 1. 先理解最普通的情况：你在电脑上写 C 程序

你写了一个程序，里面有这样一行：

```c
int *p = malloc(100);
```

这行代码背后发生了什么？

```
你的程序调用 malloc(100)
        │
        ▼
  操作系统内核
   ┌──────────────────────────────┐
   │  管理着整台机器的物理内存       │
   │  收到请求：给我 100 字节        │
   │  从空闲区域切 100 字节给你      │
   │  返回这块内存的起始地址          │
   └──────────────────────────────┘
        │
        ▼
  你的程序拿到指针 p，可以用这 100 字节了
```

操作系统手里有**一整台机器的全部内存**，谁要就给谁切一块。你用完了 `free(p)`，这块内存还给操作系统，操作系统可以再给别人用。

**这就像你去餐厅吃饭，餐厅的厨房（操作系统）有全部食材，你点一道菜，厨师现做。**

---

## 2. 深入理解：malloc 到底分配的是什么？

看完上面，你可能会觉得：`malloc(100)` 就是从操作系统手里拿了 100 字节的物理内存。

**这个理解其实不准确。** `malloc` 拿到的只是"虚拟地址的承诺"，真正的物理内存要到后面才会慢慢兑现。

### 2.1 虚拟地址空间 ≠ 物理内存

Linux 上每个进程都有自己的**虚拟地址空间**，32 位进程是 4GB，64 位进程是 256TB。这个空间在进程创建的那一刻就存在了，但它只是一个"地址目录"——大部分地址一开始是**空的**，没有对应的物理内存。

```
进程的虚拟地址空间（一开始）：

0x00000000 ┌──────────────────────┐
           │  代码段 (.text)       │  ← 映射到了真正的物理内存
           │  (你的程序指令)        │
           ├──────────────────────┤
           │  数据段 (.data/.bss)  │  ← 也映射了
           ├──────────────────────┤
           │  堆 (heap)            │  ← 一开始很小（可能只有几页）
0x???????? ├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤      brk 指针指向这里
           │                      │
           │   巨大的未映射区域      │  ← 这些地址"存在"但还没对应任何物理内存
           │                      │     就像空号电话，打了没人接
           │                      │
           ├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
           │  栈 (stack)           │  ← 映射了
0xFFFFFFFF └──────────────────────┘
```

### 2.2 malloc 只记账，不交货

```c
int *p = malloc(100 * 1024 * 1024);  // 要 100MB
```

malloc 做的事：

```
堆区域：
         brk 指针（当前堆顶）
              │
... ├─────────┤
    │ 已映射   │  ← 之前 malloc 过的一些小块
    ├─────────┤
    │         │  ← 现在要扩 100MB
    │         │
    │         │  malloc 调用 brk()/mmap()，把 brk 指针往上移
    │         │  操作系统说："好，这 100MB 虚拟地址归你了"
    │         │
    │         │  但此时：这 100MB 的每个 4KB 页面，
    │         │  都只是"记了一笔账"，还没有实际的物理页！
    │         │
    ├─────────┤  ← brk 指针移到这里
    │ 未映射   │
```

你可以做一个实验验证：

```c
// 分配 1GB
char *p = malloc(1024 * 1024 * 1024);
printf("malloc 成功，地址 = %p\n", p);

// 此时用 top/htop 看进程的虚拟内存（VSZ）涨了 1GB
// 但物理内存（RSS）几乎没变！
// 因为这 1GB 还没真正碰过
```

### 2.3 物理内存什么时候到位？

要等到**你第一次读写**这块内存的那一页时。

```
你写 p[0] = 'A';
     │
     ▼
CPU 尝试访问这个虚拟地址
     │
     ▼
MMU（内存管理单元）查页表 → 发现这个虚拟页没有对应的物理页
     │
     ▼
触发 page fault（缺页异常）
     │
     ▼
操作系统内核介入：
  1. 从空闲物理页池里拿一个 4KB 物理页
  2. 把它映射到这个虚拟地址
  3. 页表里记上：虚拟页 X → 物理页 Y
  4. 返回用户态，重新执行 p[0] = 'A'
     │
     ▼
这次访问成功了！
```

这个过程叫 **demand paging（按需调页）**——物理内存只在真正用时才以 4KB 为单位逐页分配。

### 2.4 全程时间线

```
时间线 ─────────────────────────────────────────→

1. 进程创建
   虚拟地址空间 → 存在
   物理内存     → 只映射了代码段、数据段、栈等基本区域

2. malloc(100MB)
   虚拟地址空间 → 多了 100MB 的"已预约区域"（VSZ 涨了）
   物理内存     → 没变！（RSS 没变）

3. 第一次写 p[0] = 'A'
   物理内存     → +4KB（只有被写的那一页被映射）

4. 继续写 p[4096] = 'B'   ← 跨了下一页
   物理内存     → 又 +4KB

5. 读写了全部 100MB ...
   物理内存     → 最多 +100MB（全部页都被碰过）
```

### 2.5 这个认知为什么重要

| 你可能以为 | 实际情况 |
|---|---|
| malloc 返回的是物理内存 | malloc 返回的是虚拟地址，物理内存延迟分配 |
| malloc(1GB) 需要 1GB 空闲物理内存 | 只要有 1GB 虚拟地址空间就行，物理内存可以先欠着 |
| 分配了内存不用就不占资源 | 对，确实不占物理内存，但你占用了虚拟地址空间 |
| free 把内存还给操作系统 | 不一定，free 可能只是标记为空闲但不收缩堆 |

有了这个认知，你再回头看 WAMR Pool 模式就更清晰了：**Pool 模式跳过了"虚拟地址 → 物理内存"的惰性映射机制**，直接用一块实实在在的物理内存（在裸机上本来就是直接操作物理地址），在上面自建小型的 malloc/free 系统。因为裸机没有 MMU，没有虚拟地址，所有地址都是物理地址，所以 WAMR 必须自己管好这块地上的一切。

## 3. 嵌入式场景的问题

现在换一个场景：你有一块 STM32 单片机，**没有操作系统**。

```
整块芯片只有 64KB SRAM：
┌───────────────────────────────┐
│         64KB SRAM             │  全部可用内存就这么大
│                               │
│  你的程序 + 数据 + 栈 + 堆     │  所有东西共享这 64KB
│                               │
└───────────────────────────────┘
```

问题来了：

### 问题 1：没有 `malloc`

`malloc` 是 C 标准库给的。C 标准库里 `malloc` 的实现（比如 glibc 里的 ptmalloc）非常复杂，自己就要占几十 KB 的代码，而且内部数据结构也需要额外内存。在 64KB 的单片机上，你连标准库都塞不进去，更别说 `malloc` 了。

### 问题 2：碎片化

即使你真移植了一个 `malloc`，频繁的 `malloc` + `free` 会产生**内存碎片**：

```
初始状态：
┌─────────────────────────────────────────────────┐
│             全部空闲 (1000 字节)                   │
└─────────────────────────────────────────────────┘

分配 A(100B)、B(200B)、C(100B)：
┌──────┬──────────┬──────┬───────────────────────┐
│ A 用 │  B 用    │ C 用 │    空闲 (600B)          │
└──────┴──────────┴──────┴───────────────────────┘

释放 B：
┌──────┬──────────┬──────┬───────────────────────┐
│ A 用 │  空 200B  │ C 用 │    空闲 (600B)          │
└──────┴──────────┴──────┴───────────────────────┘
        ↑ 这个洞是 200B，但它被夹在 A 和 C 中间，
          无法和后面的 600B 合并

现在你想分配 300B → 失败！
明明总空闲 = 200 + 600 = 800B，但被碎片化了，连不了
```

这就像停车场里虽然总共有 50 个空位，但每个都是分散的单个位置，无法停一辆大巴。

### 问题 3：不可预测

嵌入式系统通常有**硬实时要求**——必须在多少微秒内完成某个操作。`malloc` 的耗时不可预测（它可能要在很长的空闲链表里搜一个合适的块），实时系统最怕这个。

## 4. 内存池是什么——生活类比

### 类比：包租公模式

**没有内存池**（每次找操作系统要）：

```
你每次需要办公室 → 打电话给全城的地产商（操作系统）
                  → 地产商在整个城市（全部物理内存）里找空房间
                  → 给你钥匙
                  → 用完还回去

问题：地产商可能要在几百栋楼之间找，慢；而且办公室之间可能隔很远
```

**使用内存池**：

```
你提前租下整层楼（一块大内存）
        │
        ▼
┌────────────────────────────────────────────┐
│           你租的这层楼（内存池）              │
│                                            │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────────┐ │
│  │  A   │ │  B   │ │ 空着  │ │    C     │ │
│  └──────┘ └──────┘ └──────┘ └──────────┘ │
│                                            │
└────────────────────────────────────────────┘

以后需要房间 → 自己从这层楼里分配，不用再找地产商
用完房间   → 标识为空闲，还给自己

优势：
  - 快：只在"自己这层楼"范围内操作，不经过操作系统
  - 可控：这层楼大小固定，内存用量可控
  - 无外部碎片：整层楼就是一块连续空间
```

## 5. 内存池在代码里长什么样

最粗暴、最简陋的内存池实现：

```c
// 第一步：划一块固定大小的内存
uint8_t pool[4096];  // 你的"这层楼"，4KB

// 第二步：用一个指针记录"用到了哪里"
uint32_t used = 0;

// 第三步：分配函数
void *pool_malloc(uint32_t size) {
    if (used + size > 4096) return NULL;  // 不够了
    void *ptr = &pool[used];
    used += size;
    return ptr;
}

// 但是！这个版本有一个致命问题：
// 你永远无法释放中间的对象，只能按顺序"用到底"
// pool_free() 根本不存在
```

这就是**最简单的 bump allocator**（撞针分配器）。WAMR 当然不能这么干——它需要释放中间的对象，所以需要更复杂的数据结构。

## 6. WAMR 的 Pool 模式：把一块大内存切成可以回收的小块

### 6.1 初始化：圈定地盘

```c
// 用户在嵌入式设备上预留一块内存
uint8_t heap_buf[256 * 1024];  // 256KB

// 告诉 WAMR：用这块内存做你的池
wasm_runtime_memory_init(Alloc_With_Pool,
    &(MemAllocOption){
        .pool = {
            .heap_buf  = heap_buf,
            .heap_size = sizeof(heap_buf)
        }
    });
```

WAMR 内部做了一件事：

```
用户传入的 256KB 原始内存块：
┌──────────────────────────────────────────────────────┐
│                 256KB 原始字节数组                      │
└──────────────────────────────────────────────────────┘

WAMR 把它重塑为：
┌────────────────────┬─────────────────────────────────┐
│  gc_heap_t 结构体   │          数据区                  │
│  (~300 bytes)      │  (剩下的全部，~255KB)             │
│                    │                                 │
│  存储：            │  这部分用来切分给后来的            │
│  · 空闲链表头指针   │  每个 wasm_runtime_malloc 请求    │
│  · 红黑树根节点     │                                 │
│  · 统计信息        │                                 │
│  · 互斥锁          │                                 │
└────────────────────┴─────────────────────────────────┘
     ▲                         ▲
  元数据区                   数据区（可切分）
```

### 6.2 每次分配：怎么切

假设你已经初始化完了，现在有人调用 `wasm_runtime_malloc(100)`。

WAMR 不直接返回原始字节，而是给每一块分配的内存加一个**4 字节的小标签**（叫 HMU = Heap Memory Unit）：

```
你请求 100 字节
       │
       ▼
实际分配 = 4 字节标签 + 100 字节用户数据 = 104 字节
          （还要 8 字节对齐）

┌──────────┬──────────────────────────────┐
│ 标签     │  你的 100 字节                 │
│ (4 bytes)│                              │
├──────────┴──────────────────────────────┤
│  标签里记录了：                           │
│  · 这块的状态（在用 / 空闲）               │
│  · 这块的大小                            │
└─────────────────────────────────────────┘
```

### 6.3 释放的时候：标记为空闲，不是真的还给操作系统

```c
wasm_runtime_free(ptr);
```

这不会把内存还给操作系统（因为本来就不是从操作系统拿的）。它只做一件事：**把标签里的状态从"在用"改成"空闲"**。

```
释放前：
┌────────┬──────────┐ ┌────────┬──────────┐ ┌────────┬──────────┐
│ 在用 A │ 数据 A   │ │ 在用 B │ 数据 B   │ │ 在用 C │ 数据 C   │
└────────┴──────────┘ └────────┴──────────┘ └────────┴──────────┘

释放 B 后：
┌────────┬──────────┐ ┌────────┬──────────┐ ┌────────┬──────────┐
│ 在用 A │ 数据 A   │ │ 空闲!  │ (垃圾数据)│ │ 在用 C │ 数据 C   │
└────────┴──────────┘ └────────┴──────────┘ └────────┴──────────┘
                           ↑ B 的空间被标记为"空闲"，可以被后续分配复用
```

### 6.4 怎么找到合适的空闲块——WAMR 的"双层寻块"策略

WAMR 内部维护了两个结构来追踪空闲块：

```
空闲块追踪系统

┌──────────────────────────────────────────┐
│  ① 普通链表（32 个槽位）                   │
│                                          │
│  槽 0 → 8 字节的空闲块链表                 │
│  槽 1 → 16 字节的空闲块链表                │
│  槽 2 → 24 字节的空闲块链表                │
│  ...                                     │
│  槽 31 → 248 字节的空闲块链表              │
│                                          │
│  像停车场按车型分区：                       │
│  摩托车区、小轿车区、SUV区、卡车区            │
│  来了一个中型车，直接去 SUV 区找             │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│  ② 红黑树（处理大块）                      │
│                                          │
│  大于 248 字节的空闲块不放在链表里，          │
│  而是按大小插入到一棵红黑树中               │
│                                          │
│  树的结构保证：                            │
│  左子树 ≤ 当前节点 < 右子树                │
│  查找 best-fit 很快                       │
└──────────────────────────────────────────┘
```

**分配时流程：**

```
wasm_runtime_malloc(100)
        │
        ▼
100 + 4 字节标签 = 104 → 对齐到 8 的倍数 = 104 字节
        │
        ▼
104 < 248，走普通链表
        │
        ▼
计算槽位：104 / 8 = 13 → 去第 13 号槽找
        │
        ├── 第 13 号槽有 112 字节的空闲块 → 直接取出来给你
        │
        └── 第 13 号槽是空的 → 继续查 14、15、16...
                │
                ├── 找到了一个 200 字节的空闲块
                │   → 切 104 字节给你，剩 96 字节放回槽 12
                │
                └── 一直到槽 31 都没有
                    → 去红黑树里找
                    → best-fit：选最接近 104 字节的块
```

### 6.5 补充：红黑树是什么，为什么用它

上面提到"去红黑树里找"，你可能只有一个模糊的印象——"哦，一种树"。这里把红黑树讲清楚。

#### 6.5.1 从最笨的找法说起

假设你有 50 个大小各异的空闲块，现在需要一块 300 字节的。最笨的办法：

```c
// 线性遍历：从头到尾看一看
void *best = NULL;
for (每个空闲块) {
    if (块大小 >= 300 && (best == NULL || 块大小 < best->大小)) {
        best = 当前块;
    }
}
// 每次都要看完 50 个块，O(n)
```

对于小块（≤248 字节），WAMR 的 32 槽普通链表已经够快了——因为按大小分槽，到了对应槽位直接取链表的第一个节点就行，基本 O(1)。

但**大块不能这么搞**。大块从 256 字节到上 KB 不等，大小跨度很大，没办法用固定步长的槽位覆盖。如果有 100 个几百字节到几 KB 的大块散落在内存里，每次都要遍历全部 100 个，太慢了。

#### 6.5.2 树的思路

把空闲块按大小排成**树形结构**：

```
           ┌─────────┐
           │  512B   │  ← 根节点
           │  (空闲)  │
           └────┬────┘
       ┌────────┴────────┐
  ┌─────────┐       ┌─────────┐
  │  256B   │       │ 1024B   │
  │  (空闲)  │       │  (空闲)  │
  └─────────┘       └────┬────┘
                     ┌─────┴─────┐
                ┌─────────┐ ┌─────────┐
                │  768B   │ │ 2048B   │
                │  (空闲)  │ │  (空闲)  │
                └─────────┘ └─────────┘
```

**规则**：左子树的大小 ≤ 当前节点 < 右子树的大小（WAMR 的实现）。

#### 6.5.3 在树上找 300 字节的块

```
从根节点 512B 开始：512 ≥ 300 → 记录 512B 是候选 → 去左子树看看有没有更小的
        │
        ▼
左子树是 256B：256 < 300 → 太小，不符合 → 去右子树找
        │
        ▼
256B 没有右子树了 → 搜索结束
返回之前记录的最佳候选：512B
```

**只需要比较 2 次就找到了**。如果 100 个块平铺在链表里，最坏要比较 100 次；放在平衡的树里，最多比较约 7 次（log₂(100) ≈ 7）。

#### 6.5.4 但普通二叉搜索树会"退化"

如果空闲块恰好按大小顺序插入（比如 100, 200, 300, 400...），普通二叉搜索树会变成一条链：

```
100
 └── 200
      └── 300
           └── 400
                └── ...
```

一条链 = 一个链表，查找退回 O(n)，白建了。

#### 6.5.5 红黑树解决了这个问题

**红黑树是一种"自平衡"的二叉搜索树。** 它在每次插入和删除后，通过**变色 + 旋转**自动调整树的形状，保证不会退化成一条链。

```
规则（简化版）：
  1. 每个节点要么红要么黑
  2. 根节点是黑的
  3. 红色节点的子节点必须是黑的（不能两个红色连着）
  4. 从任一节点到其所有叶子节点的路径上，黑色节点数量相同

只要满足这四条，树的高度就自动保持在 O(log n)，
查找、插入、删除全部 O(log n)。
```

#### 6.5.6 为什么 WAMR 选红黑树

| 数据结构 | 查找 | 插入 | 删除 | 适合 |
|----------|------|------|------|------|
| 数组 | O(n) | O(n) | O(n) | 不行 |
| 排序数组 | O(log n) 二分 | O(n) 要搬元素 | O(n) | 不行，碎片频繁变化 |
| 单向链表 | O(n) | O(1) | O(n) | 小块还行，大块太慢 |
| 普通二叉搜索树 | O(log n) 平均 | O(log n) | O(log n) | 可能退化成 O(n) |
| **红黑树** | **O(log n)** | **O(log n)** | **O(log n)** | **最坏情况也有保证** |
| AVL 树 | O(log n) | O(log n) 更贵 | O(log n) 更贵 | 查找更快但修改更贵 |

**红黑树是插入/删除 vs 查找之间的最佳平衡。** 内存分配场景下，分配（删除）+ 释放（插入）和查找几乎一样频繁，红黑树的插入成本比 AVL 树低，查找仍然是 O(log n)，非常适合。

#### 6.5.7 在 WAMR 代码里

```c
// ems_gc_internal.h:419-425
typedef struct hmu_tree_node {
    hmu_t hmu_header;              // 4 字节 HMU 头部，双用途
    struct hmu_tree_node *left;    // 左子节点
    struct hmu_tree_node *right;   // 右子节点
    struct hmu_tree_node *parent;  // 父节点
    gc_size_t size;                // 节点大小（用于排序比较）
} hmu_tree_node_t;
```

有趣的是：**红黑树节点和空闲块是同一个东西**。一个空闲 HMU 被放入红黑树时，它的数据区正好用来存 `left`、`right`、`parent` 三个指针。不需要额外分配树节点——树就是嵌入在空闲块里的。

```
一个空闲大块在红黑树中：
┌──────────┬──────────────────────────────────────────┐
│ HMU 头部 │  left 指针 │ right 指针 │ parent 指针 │ size │
│ (4 bytes)│  (8 bytes) │ (8 bytes)  │ (8 bytes)   │(8B)  │
└──────────┴──────────────────────────────────────────┘
    ▲                                        │
    └── hmu_header ── 同时是树节点的头部 ──────┘
```

**这叫"侵入式数据结构"（intrusive data structure）**——树节点不独立分配，而是寄生在它要管理的数据块内部。省内存、省分配，在嵌入式场景下这是标配做法。

#### 6.5.8 一句话总结红黑树

**红黑树 = 一棵会自动保持平衡（不会退化成链）的二叉搜索树。** WAMR 用它管理大于 248 字节的空闲块，保证在最坏情况下查找/插入/删除都是 O(log n)。而且树节点直接嵌入在空闲块里，零额外内存开销。

## 7. 内存池 vs malloc：到底有什么区别？

到现在你可能有一个疑问：内存池自己和 malloc 做的事情看起来差不多——都是分配释放内存，那到底有什么区别？

### 7.1 一句话区别

**malloc 背后是操作系统，内存池是你自家院子里的一块地。**

| | malloc | 内存池 |
|---|---|---|
| **内存从哪来** | 操作系统（内核） | 你自己提前准备好的一块固定内存 |
| **谁在管理** | glibc 的 ptmalloc / jemalloc 等分配器 | 你自己的分配器（比如 WAMR 的 EMS） |
| **分配范围** | 整个进程的虚拟地址空间 | 只在你给的那块内存里 |
| **能不能动态扩容** | 能，操作系统自动帮你扩堆 | 不能，池大小是固定的 |

### 7.2 类比

```
malloc 方式：
  你需要一张办公桌 → 打电话给行政（操作系统）
                   → 行政在整个办公大楼里找空房间
                   → 给你钥匙
                   → 用完还回去
                   → 房间可能在东区，下次可能在西区

内存池方式：
  你提前租下 203 室一整间
  在里面摆了 10 张桌子
  以后有人要桌子 → 直接从 203 室里拿一张
  用完放回 203 室
  所有桌子都在 203 室里，你完全掌控
```

### 7.3 是否依赖操作系统

```c
// malloc：必须有 OS
int *p = malloc(100);
// 内部可能调用 brk() 或 mmap()，这些都是系统调用
// 裸机上根本调不了

// 内存池：不需要 OS
uint8_t pool[4096];
void *p = pool_malloc(100);
// 只是在数组里标记"这 100 字节被用了"
// 裸机上完全能跑
```

### 7.4 能否动态扩容

```c
// malloc：申请多少都可以（直到虚拟地址空间用尽）
int *p1 = malloc(100 * 1024 * 1024);  // 100MB，行
int *p2 = malloc(500 * 1024 * 1024);  // 500MB，也行
// 操作系统自动给堆扩空间

// 内存池：超过池大小就失败
uint8_t pool[256 * 1024];  // 只有 256KB
void *p = pool_malloc(300 * 1024);  // 要 300KB → 返回 NULL
// 池多大就只能用多大，不能扩
```

### 7.5 碎片的管理者不同

```
malloc：
  碎片由 glibc 处理（ptmalloc 内部有复杂的 bin 和 arena 机制）
  但外部碎片你控制不了——两个相邻的 free 块在 glibc 内部可能
  属于不同 arena，永远不会合并

内存池：
  碎片由你自己的分配器处理
  WAMR 的 EMS 会在 free 时检查相邻块，如果邻居也空闲就合并
  碎片策略完全受你掌控
```

### 7.6 性能的可预测性

```
malloc(100)：
  → glibc 内部可能要查 fastbin → smallbin → largebin → 找 top chunk
  → 可能触发 brk() 系统调用
  → 耗时不可预测（纳秒级到毫秒级都有可能）

pool_malloc(100)：
  → 查一下空闲链表（最多 32 个槽位扫一遍）
  → 没有就去红黑树 best-fit
  → 耗时高度可预测，没有系统调用
```

### 7.7 总结

**malloc 背后是操作系统，操作系统是一个巨大的黑盒，你不知道它在干什么。**

- 在嵌入式场景下，你**没有**操作系统这个黑盒可以依赖，所以只能自己管
- 在桌面场景下，你用内存池是为了**不让黑盒影响你**——确定性、可预测性、可控性
- 即使有 OS 的场景，WAMR 默认的 Pool 模式也能避免 glibc 碎片对 wasm 运行时的干扰

## 8. EMS 本质上就是一个小 malloc

如果你已经理解了 glibc 的 `malloc`/`free` 的设计思路，再看 WAMR 的 EMS，会发现它是**同一个配方，缩小的分量**。

### 8.1 结构对照

两边都是：把一块大内存（堆）切成很多 HMU/chunk，每块前面挂一个头部记录"这块多大、在用还是空闲"，空闲块挂在链表/树上等待分配。

| 概念 | glibc ptmalloc | WAMR EMS |
|---|---|---|
| 堆的来源 | 进程虚拟地址空间，通过 `brk()`/`mmap()` 动态扩缩 | 用户预分配的一块固定物理内存 |
| 每个块的头部 | `malloc_chunk` 结构体（16 bytes） | HMU 4 字节 header（bitfield） |
| 空闲块组织 | **多级 bin 系统**：fastbins → smallbins → largebins → unsorted bin | **两层结构**：32 槽普通链表 → 红黑树 |
| 大块分配 | `mmap()` 直接映射（单独管理，不走堆） | 没有，全在池内，大了就失败 |
| 空闲块合并 | 释放时检查前后 chunk 的 `PREV_INUSE` bit，合并后放入 unsorted bin | 释放时检查相邻 HMU 的 P bit，通过 `gci_add_fc` 合并 |
| 线程安全 | 多 arena：每个线程有自己的堆区，减少锁竞争 | 一把全局锁（`korp_mutex`），整个堆串行化 |
| 代码量 | ptmalloc ~5000+ 行 | EMS ~1000 行 |

### 8.2 两边在"找空闲块"上的对应关系

```
glibc ptmalloc 的查找路径：
  malloc(100)
    → 从线程所属 arena 开始
    → 查 fastbins（很小的块，LIFO，不合并）
    → 查 smallbins（≤512B 的块）
    → 查 largebins（大块，按大小排序）
    → 都没有 → 从 top chunk 切一块新的
    → top chunk 不够 → sbrk() 向操作系统要更多堆

WAMR EMS 的查找路径：
  wasm_runtime_malloc(100)
    → 从 pool_allocator（唯一堆）开始
    → 查 32 槽普通链表（≤248B 的块，每槽步长 8B）
    → 查红黑树（>248B 的块，按大小排序）
    → 都没有 → 触发 GC（仅 WO 对象）
    → 还是没有 → 返回 NULL（池固定，没法扩）
```

你会发现流程结构几乎一样：**按大小分级 → 小快的快速路径 → 大块的树/排序路径 → 兜底策略**。区别只是 glibc 的 bin 系统更细密（6 种 bin 类型），EMS 只分两档。

### 8.3 EMS 简化了什么

WAMR 是给嵌入式做的，所以把 glibc 里的"重型装备"全砍了：

**砍了多线程支持：** glibc 有多个 arena 来减少多线程竞争，EMS 只有一把锁。嵌入式设备本来也少有几十个线程同时分配内存。

**砍了动态扩堆：** glibc 可以 `sbrk()` 让堆变大，`malloc_trim()` 把空闲内存还给 OS。EMS 池大小固定，无法扩缩——嵌入式场景下内存就那么多，扩也没地方扩。

**砍了 mmap 大块通道：** glibc 对大块（>128KB）直接用 `mmap()` 单独映射，不走堆。EMS 没有操作系统，所有分配全在池内。

**砍了 chunk 头部大小：** glibc 的 `malloc_chunk` 在 64 位系统上占 16 字节（prev_size + size + fd + bk），EMS 的 HMU 只有一个 4 字节 header。

### 8.4 本质上是同一个东西

```
glibc malloc：管理"整个城市"的土地（进程虚拟地址空间）
WAMR  EMS：管理"一层楼"的房间（用户给的固定内存块）

工具不同，手艺一样：切块、标记、查找、合并。
```

这也是为什么你在 WAMR 的代码里能看到 `gc_alloc_vo`、`gc_free_vo`、`alloc_hmu`、`gci_add_fc` 这些函数名——它们做的事情和 glibc 里的 `_int_malloc`、`_int_free`、`unlink_chunk`、`malloc_consolidate` 本质上是对应的。

## 9. 用一个完整例子串起来

```
假设你有 1024 字节的内存池，已经初始化好。

═══════════════════════════════════════════════════
初始状态：整个数据区是一个大空闲块 (FM)
┌────────────────────────────────────────────────┐
│  标签: 空闲, 大小 1024                           │
╞════════════════════════════════════════════════╡
│             全部空闲                              │
└────────────────────────────────────────────────┘

═══════════════════════════════════════════════════
步骤 1: wasm_runtime_malloc(100)
         ↓
        标签: "在用 VO, 大小 104"
        剩余: 空闲, 大小 920
┌────────┬──────────────────────────────────────┐
│ A  104B│              空闲 920B                 │
└────────┴──────────────────────────────────────┘

═══════════════════════════════════════════════════
步骤 2: wasm_runtime_malloc(200)
         ↓
        标签: "在用 VO, 大小 208"
        剩余: 空闲, 大小 712
┌────────┬──────────┬──────────────────────────┐
│ A  104B│ B   208B │        空闲 712B           │
└────────┴──────────┴──────────────────────────┘

═══════════════════════════════════════════════════
步骤 3: wasm_runtime_free(A)
         ↓
        A 被标记为空闲 (becomes FC - Free Coalesced)
        注意：A 和后面的 B 还不能合并（B 还在用）
┌────────┬──────────┬──────────────────────────┐
│ 空闲   │ B   208B │        空闲 712B           │
└────────┴──────────┴──────────────────────────┘

═══════════════════════════════════════════════════
步骤 4: wasm_runtime_free(B)
         ↓
        B 被标记为空闲
        WAMR 发现 A、B 和后面的空闲块挨在一起 → 合并！
┌────────────────────────────────────────────────┐
│         一块 1024 字节的空闲空间                   │
│          回到了初始状态！                         │
└────────────────────────────────────────────────┘
```

**关键点：** WAMR 在 free 时会检查相邻块，如果邻居也是空闲的就把它们**合并**（coalesce）。没有合并的空闲块还可以被插入到红黑树里。

## 10. 为什么 Pool 模式适合嵌入式

回到最初的问题——为什么嵌入式场景需要内存池？

| | 传统 malloc | WAMR Pool 模式 |
|---|---|---|
| **依赖操作系统** | 是 | 否 |
| **内存来源** | 操作系统内核分配 | 用户预先提供的一块固定内存 |
| **碎片控制** | 可能有外部碎片 | 一块连续空间，合并相邻空闲块 |
| **内存上限** | 受系统空闲内存影响 | 固定的，用户知道确切上限 |
| **实时性** | 不可预测（可能要系统调用） | 可预测（只在池内操作，加一把锁） |
| **代码体积** | 标准库 malloc 很大 | EMS 分配器只有 ~1000 行 C 代码 |
| **调试** | 碎片难排查 | 池大小固定，可以整体检查 |

## 11. 三种模式怎么选

现在你应该能理解三种模式的本质区别了：

```
你有一块地需要用：

Pool 模式：                      Allocator 模式：               System 模式：
┌──────────────────────┐      ┌──────────────────────┐      ┌──────────────────────┐
│  你提前买下一块地       │      │  你雇一个包工头          │      │  每次直接找市政府要地    │
│  在上面规划好房间       │      │  每次要房间就告诉包工头   │      │  市政府有全部土地        │
│                      │      │  他去找地、建房         │      │  来者不拒               │
│  WAMR 自带分配器       │      │  你自己实现 malloc/free │      │  直接用系统 malloc      │
│  (EMS 或 TLSF)       │      │  注入到 WAMR 里        │      │                       │
└──────────────────────┘      └──────────────────────┘      └──────────────────────┘

适用：裸机 / RTOS              适用：你已有的 RTOS 上有      适用：Linux/macOS/Windows
      没有 malloc               自己的分配器                    有完整 libc
      内存精确可控              想统一管理所有内存              不在乎内存碎片
```

## 12. 一句话总结

**内存池就是"预先拿一块固定大小的内存，然后自己在上面实现小型的 malloc/free"。** 不做池，每次分配都要找操作系统（嵌入式上可能根本没有）；做了池，所有分配释放都在自己的地盘里，快速、可控、可预测。WAMR 的 EMS 分配器就是这块地盘上的"包租公"，用 4 字节标签追踪每一块的状态，用 32 槽链表 + 红黑树高效找到合适的空闲块。
